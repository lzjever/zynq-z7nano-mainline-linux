CHAPTER 04

构建三件套:U-Boot、内核、Debian rootfs

三条流水线,一台普通 x86 Ubuntu 24.04,零 Vivado——每一条命令都可以直接复制执行。

第 2 章讲过启动链是 BootROM → FSBL → U-Boot → 内核 → 用户态。其中 FSBL 我们直接复用厂商现成的——它的灵魂 ps7_init 携带每块板不同的板级参数(第 2 章),自己重编收益有限。剩下三环,就在本章亲手造出来:

4.2 U-Boot(主线源码 + 我们的设备树)→ u-boot-dtb.bin
↓
4.3 Linux 内核(multi_v7 + 同源设备树)→ zImage、dtb、899 个模块
↓
4.4 Debian rootfs(debootstrap + qemu 伪装)→ 一整棵 Debian 13
↓
三路产物在 第 5 章汇合:装进一张 SD 卡,首次启动

三条流水线彼此独立,顺序无所谓;设备树(4.2、4.3 各一棵)是唯一贯穿的线索,也是每块板真正的"板级支持包"。

4.1 出发前:目录约定与依赖一次装齐

先把工作台搭好。全手册统一使用这套目录:源码进 src,编译产物进 build,Debian 根文件系统长在 rootfs,等待上卡的启动文件放进 sd,厂商资料放 vendor。

# 工作台目录约定(全手册沿用;尽量写绝对路径,sudo 下 ~ 会展开成 /root)
mkdir -p ~/zynq-mainline/{src,build,rootfs,sd,vendor}

本章全程需要联网——克隆源码、apt 装包、debootstrap 下载 Debian,一个都少不了。然后一条 apt 把所有依赖装齐,这是"本项目不需要 Vivado"的第一份证据:

4.2 U-Boot:主线源码 + 一份设备树

第一步:克隆主线源码

cd ~/zynq-mainline/src
git clone --depth 1 https://github.com/u-boot/u-boot.git   # 浅克隆,只取最新主线

第二步:放入 Z7-Nano 的设备树(全文)

主线 U-Boot 不认识 Z7-Nano,我们要给它一份设备树。以下是我们实测可用的 zynq-z7-nano.dts 全文——把它放进 arch/arm/dts/。逐段的门道在代码后面讲。

// SPDX-License-Identifier: GPL-2.0+
/*
 * MicroPhase Z7-Nano R20 (XC7Z020) — U-Boot device tree
 * Based on zynq-zed.dts; console on uart0, 512MB DDR,
 * RTL8211F PHY at MDIO addr 1 with reset on MIO46.
 */
/dts-v1/;
#include "zynq-7000.dtsi"
#include <dt-bindings/gpio/gpio.h>

/ {
	model = "MicroPhase Z7-Nano R20";
	compatible = "microphase,zynq-z7-nano", "xlnx,zynq-7000";

	aliases {
		ethernet0 = &gem0;
		serial0 = &uart0;
		mmc0 = &sdhci0;
	};

	memory@0 {
		device_type = "memory";
		reg = <0x0 0x20000000>;
	};

	chosen {
		bootargs = "";
		stdout-path = "serial0:115200n8";
	};

	usb_phy0: phy0 {
		compatible = "usb-nop-xceiv";
		#phy-cells = <0>;
	};
};

&clkc {
	ps-clk-frequency = <33333333>;
};

&gem0 {
	status = "okay";
	phy-mode = "rgmii-id";
	phy-handle = <&ethernet_phy>;

	ethernet_phy: ethernet-phy@1 {
		reg = <1>;
		reset-gpios = <&gpio0 46 GPIO_ACTIVE_LOW>;
	};
};

&sdhci0 {
	bootph-all;
	status = "okay";
};

&uart0 {
	bootph-all;
	status = "okay";
};

&usb0 {
	status = "okay";
	dr_mode = "host";
	usb-phy = <&usb_phy0>;
};

第三步:逐段讲解——与模板的四处关键差异

骨架套路:先 #include "zynq-7000.dtsi"——那是一颗 Zynq SoC 的"出厂清单",把所有外设都列好了但全部 status = "disabled";板级 dts 只做三件事:挑设备打开(okay)、给板级参数(内存大小、时钟、PHY)、指控制台。我们仿 zynq-zed.dts,真正动过的地方就四处:

差异一:控制台在 uart0,不是 uart1。Zed/Zybo 的传统控制台是 uart1,但 Z7-Nano 板上唯一启用的串口是 UART0 @ 0xE0000000,经 CH340E 接到 type-C "UART" 口(硬件上第二个串口根本没开时钟)。所以别名必须指对:

aliases {
	serial0 = &uart0;      /* stdout-path 里的 "serial0" 靠这行解析到 UART0 */
};
chosen {
	stdout-path = "serial0:115200n8";   /* 115200 8N1 */
};

指错串口的症状很有迷惑性:U-Boot 明明在跑(第 6 章 JTAG 能看到 PC 在动),串口却一个字都不出。

差异二:内存 512MB。内存大小每块板不一样,必须照实配写——Z7-Nano 贴的是 512MB DDR3:

memory@0 {
	device_type = "memory";
	reg = <0x0 0x20000000>;   /* 起始 0x0,长度 0x20000000 = 512MB */
};

内存起点 0x0 是 Zynq 的规矩(DDR 直接映射到地址 0);写多了会在顶部踩空,写少了浪费。板上实际跑起来内核可见约 479MB,顶端一小段是保留区,正常现象。

差异三:PHY 在 MDIO 地址 1,复位脚 MIO46。板上的网口是 Zynq GEM(gem0)挂一颗 Realtek RTL8211F:

&gem0 {
	status = "okay";
	phy-mode = "rgmii-id";                 /* RGMII,收发延迟由 PHY 内部提供 */
	phy-handle = <&ethernet_phy>;
	ethernet_phy: ethernet-phy@1 {
		reg = <1>;                              /* PHY 挂在 MDIO 总线地址 1 */
		reset-gpios = <&gpio0 46 GPIO_ACTIVE_LOW>;  /* PHY 复位脚 = MIO46,低有效 */
	};
};

两个实战要点:其一,这个 reg = <1> 当初是拍脑袋猜的——后来上电,内核日志里的 PHY [...:01] 证实恰好命中。不想猜的话,先写 0 或干脆不写 phy 节点更稳妥,macb 驱动会对整个 MDIO 总线扫描找出真实地址;其二,节点里没有写 PHY 型号,这是故意的,原因见 4.5 节第三堂课。

差异四:USB 设成 host 模式。板上是 USB3320 ULPI PHY,配一个"无操作收发器"占位驱动就够:

usb_phy0: phy0 {
	compatible = "usb-nop-xceiv";   /* nop = 占位 PHY,真实 ULPI 不需要内核驱动 */
	#phy-cells = <0>;
};
&usb0 {
	status = "okay";
	dr_mode = "host";               /* 当主机用:插 U 盘、键盘等 */
	usb-phy = <&usb_phy0>;
};

其余节点(sdhci0、clkc 的 33.33MHz PS 时钟)与模板一致,照抄即可。另外注意每个关键节点上的 bootph-all——意思是"所有启动阶段都可能用到",U-Boot 识别这个标准属性,串口和 SD 必须尽早可用,别删。

还有两行小而重要:model 是人类可读的板名(strings 验证查的就是它);compatible 是驱动匹配用的两级身份——先报"microphase,zynq-z7-nano"(精确板号,目前没人认),再退到"xlnx,zynq-7000"(SoC 级通用匹配,真正起作用的是它)。这种"从具体到通用"的回退链是设备树的标准玩法。

第四步:注册到 Makefile

dts 放进去还不算数,要在 arch/arm/dts/Makefile 里登记一行,编译系统才会为它生成 .dtb。找到 zynq 板列表,依样画葫芦:

# arch/arm/dts/Makefile,在 zynq 系列附近加一行
dtb-$(CONFIG_ARCH_ZYNQ) += zynq-z7-nano.dtb
为什么找不到 zynq_zed_defconfig 了?

老教程会让你 make zynq_zed_defconfig——2026 年的主线里已经没有这种单板 defconfig 了。U-Boot 把 Zynq-7000 全系清理成一份 xilinx_zynq_virt_defconfig:配置不再按板子分家,板级差异全部交给设备树,编译时用 DEVICE_TREE= 变量指名道姓。内核也在 6.12 做了同样的大合并:arm32 单板 defconfig 纷纷退场,Zynq 归入 multi_v7_defconfig。

这对我们是好事:上游好维护、新板只需一棵 dts。代价是 multi_v7 是"大而全"配置(899 个模块),关键 CONFIG 是否命中要自己验——所以 4.3 节有一张验证表。

第五步:编译——用 DEVICE_TREE 覆盖默认板

cd ~/zynq-mainline/src/u-boot
# 1) 先装一份"Zynq 通吃"的默认配置
make O=$HOME/zynq-mainline/build/uboot CROSS_COMPILE=arm-linux-gnueabihf- xilinx_zynq_virt_defconfig
# 2) 编译;DEVICE_TREE= 指定我们的板子(不指定就编默认板!)
make O=$HOME/zynq-mainline/build/uboot CROSS_COMPILE=arm-linux-gnueabihf- \
     DEVICE_TREE=zynq-z7-nano -j24

-j24 按你的 CPU 核数改(整轮编译以 24 核机器为参考约 2-3 分钟,核数少的机器按比例放慢)。注意 DEVICE_TREE= 只加在第二条 make 上——defconfig 那步不需要,编译那步绝不能忘。

make O= 是什么意思?

O=目录 把编译产物全部导到指定目录,源码树保持干净(out-of-tree build)。好处有三:换一个目标(比如同时编内核和 U-Boot)互不污染;删掉重编只需 rm -rf 一个目录;源码树随时可以 git clean。本章 U-Boot 用了 O=;内核为简单起见就地编译(in-tree),产物散在源码树里,同样能跑。

第六步:验证——设备树真的嵌进去了吗

U-Boot 会把设备树编译后嵌进自身镜像。编译完用 strings 确认我们的板名确实在产物里:

strings $HOME/zynq-mainline/build/uboot/u-boot.dtb | grep MicroPhase
# 期望输出: MicroPhase Z7-Nano R20

看到 MicroPhase Z7-Nano R20 就说明 DEVICE_TREE 覆盖生效。顺手认识一下三个产物:

产物是什么 / 干什么用
u-boot-dtb.binU-Boot 主体二进制+设备树拼接的平铺镜像——第 5 章做 BOOT.BIN 第二分区就用它
u-boot带符号的 ELF——第 6 章 JTAG 调试加载用
u-boot.dtb独立的设备树 blob,刚才 strings 验证的对象

还有一件事值得知道:这份配置默认 BOOTCOMMAND="run distro_bootcmd"、BOOTDELAY=2——U-Boot 启动后倒数 2 秒,自动去 SD 卡上找 /extlinux/extlinux.conf 之类的引导菜单。这正是第 5 章"换内核只需改文件、不用重编 U-Boot"的机制基础。

这一小节最常见的几个翻车现场,对号入座:

现象原因
strings 查出来是 zed/zybo 等别的板名DEVICE_TREE= 忘了加在第二条 make 上,编的是默认板
No rule to make target …zynq-z7-nano.dtbMakefile 里没登记(第四步)

4.3 Linux 内核:multi_v7 + 同源设备树

第一步:放入内核版设备树(全文)

内核也要一份同源 dts(内核树放在 arch/arm/boot/dts/xilinx/)。它和 U-Boot 版基本一致——四差异点原样保留——只多了一点 QSPI 预留,全文如下:

// SPDX-License-Identifier: GPL-2.0+
/*
 * Device Tree for MicroPhase Z7-Nano R20 board (XC7Z020)
 * Ported from zynq-zybo-z7.dts, differences:
 *   - console on uart0 (e0000000) instead of uart1
 *   - 512MB DDR (0x20000000)
 *   - ETH PHY: Realtek RTL8211F, phy reset on MIO46 (from vendor live DT)
 *   - no MIO gpio LED (SD activity LED comes from mmc driver)
 */
/dts-v1/;
#include "zynq-7000.dtsi"
#include <dt-bindings/gpio/gpio.h>

/ {
	model = "MicroPhase Z7-Nano R20";
	compatible = "microphase,zynq-z7-nano", "xlnx,zynq-7000";

	aliases {
		ethernet0 = &gem0;
		serial0 = &uart0;
		spi0 = &qspi;
		mmc0 = &sdhci0;
	};

	memory@0 {
		device_type = "memory";
		reg = <0x0 0x20000000>;
	};

	chosen {
		bootargs = "";
		stdout-path = "serial0:115200n8";
	};

	usb_phy0: phy0 {
		#phy-cells = <0>;
		compatible = "usb-nop-xceiv";
	};
};

&clkc {
	ps-clk-frequency = <33333333>;
};

&gem0 {
	status = "okay";
	phy-mode = "rgmii-id";
	phy-handle = <&ethernet_phy>;

	ethernet_phy: ethernet-phy@1 {
		reg = <1>;
		reset-gpios = <&gpio0 46 GPIO_ACTIVE_LOW>;
	};
};

&qspi {
	bootph-all;
	status = "okay";
};

&sdhci0 {
	bootph-all;
	status = "okay";
};

&uart0 {
	bootph-all;
	status = "okay";
};

&usb0 {
	status = "okay";
	dr_mode = "host";
	usb-phy = <&usb_phy0>;
};

与 U-Boot 版的差异只有两处:多了 spi0 = &qspi 别名和 &qspi 节点——这是给将来 QSPI 启动(第 8 章路线图)留的口子;头注释里还交代了一处"没带的差异":这块板没有 MIO 上的 GPIO LED,SD 活动灯由 mmc 驱动自己点亮,所以不需要 LED 节点。同样要在 arch/arm/boot/dts/xilinx/Makefile 里登记:

# arch/arm/boot/dts/xilinx/Makefile,zynq 系列附近
dtb-$(CONFIG_ARCH_ZYNQ) += zynq-z7-nano.dtb
U-Boot 一棵树、内核一棵树,为什么要两份?

两棵 dts 语义同源(描述同一块板),但消费它们的人不同:U-Boot 把自己的那份编进 u-boot-dtb.bin,内核启动时收到的则是内核树里的那份 .dtb(由 extlinux.conf 的 fdt 行指定)。两份各自独立编译、独立演进——U-Boot 那份只需要"够开机搬运用"的设备,内核那份才是完整世界。

改了内核树里的 dts 却忘记 U-Boot 那份(或反过来)是移植期的经典乌龙:症状是"两级启动行为对不上"。好习惯:每次改板级差异,两边同步改。

第二步:配置与编译

cd ~/zynq-mainline/src
git clone --depth 1 https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux
# 1) 通用 arm32 配置(6.12 起 Zynq 单板 defconfig 已并入 multi_v7)
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- multi_v7_defconfig
# 2) 编内核、设备树、模块(-j 按核数调整)
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- -j24 zImage dtbs modules
# 3) 模块安装到独立目录,稍后拷进 rootfs
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- \
     INSTALL_MOD_PATH=$HOME/zynq-mainline/build/modules modules_install

这一步的产物(编译耗时以 24 核机器为参考约 15 分钟,核数少的机器按比例放慢):arch/arm/boot/zImage(约 11.7MB)、arch/arm/boot/dts/xilinx/zynq-z7-nano.dtb,以及 899 个 .ko 模块共约 120MB。顺手把两个"上架"文件拷到第 5 章要用的 sd 目录:

mkdir -p ~/zynq-mainline/sd/boot/extlinux
cp arch/arm/boot/zImage ~/zynq-mainline/sd/boot/
cp arch/arm/boot/dts/xilinx/zynq-z7-nano.dtb ~/zynq-mainline/sd/boot/

第三步:modules_install 的两个真实的坑

模块安装的两个坑(defconfig 的坑在第 7 章坑 6 有详录;modules 竞态重跑一遍即愈)

坑一:偶发 cp 报错。大核数并行跑 modules_install 时偶发 cp 报错,这是安装脚本内部的竞态,重跑一遍即好,不影响产物正确性——别急着重装环境。

坑二:目录层级。INSTALL_MOD_PATH 指向的是一个"根",make 会自动在其下创建 lib/modules/<内核版本>/ 层级。板上模块必须恰好位于 /lib/modules/$(uname -r)/——少一层(直接躺在 /lib/modules 下)modprobe 就一个都找不到。装完检查:

ls $HOME/zynq-mainline/build/modules/lib/modules/
# 应看到且只有一个目录——版本号取决于你克隆内核的时点,与手册的 6.18.0 不同是正常的!
# 后续命令统一用变量代替版本号,现在导出它(在内核树顶层执行):
KVER=$(make ARCH=arm kernelrelease)

第四步:.config 关键项验证表

multi_v7 大而全,但"全"不等于"对"。启动链上每一环的 CONFIG 都不能缺席,一条命令验证:

grep -E 'CONFIG_(ARCH_ZYNQ|SERIAL_XILINX_PS_UART|SERIAL_XILINX_PS_UART_CONSOLE|MACB|REALTEK_PHY|USB_CHIPIDEA|EXT4_FS|CGROUPS)=' .config
配置项预期缺了会怎样
CONFIG_ARCH_ZYNQy内核根本不支持这颗 SoC
CONFIG_SERIAL_XILINX_PS_UARTy没有 ttyPS0,串口哑掉
CONFIG_SERIAL_XILINX_PS_UART_CONSOLEy有串口驱动但当不了控制台,看不到登录提示
CONFIG_MACByGEM 以太网驱动缺失,网口消失
CONFIG_REALTEK_PHYy认不出 RTL8211F,链路起不来
CONFIG_USB_CHIPIDEAyZynq 的 USB 控制器(ChipIdea IP)没人管
CONFIG_EXT4_FSy挂不上 ext4 根分区,卡在启动中途
CONFIG_CGROUPSysystemd 起不来,用户态瘫痪

实测 multi_v7_defconfig 下这八项全部为 y,一张表安心。若你看到某项是 =m(编成模块)也不算错——只要对应的 .ko 确实进了 rootfs 模块目录。

有读者会问:能不能 menuconfig 裁一个精简内核?能,但建议先跑通通用配置再回头裁——899 个模块躺在 rootfs 里只占约 120MB,SD 卡有的是地方;第一次就追求极简,排障成本会指数上升。这也是全手册的基调:先求通,再求精。

4.4 Debian 13 rootfs:debootstrap 两阶段

第三件套是根文件系统。我们不在板上装系统,而是在 x86 主机上把一整棵 Debian 13(trixie,armhf 架构)"种"出来,稍后整树拷进 SD 卡第二分区。

第一步:--foreign 只下载、不执行

cd ~/zynq-mainline
# --foreign:第一阶段,只下载 .deb 并解包,不执行任何 ARM 程序
sudo debootstrap --arch=armhf --foreign trixie rootfs \
     https://mirrors.tuna.tsinghua.edu.cn/debian
# 把 ARM 解释器放进 rootfs(chroot 之后只能看见 rootfs 内部的文件!)
sudo cp /usr/bin/qemu-arm-static rootfs/usr/bin/
# 第二阶段:在 chroot 里把基础系统配置完整
sudo chroot rootfs /debootstrap/debootstrap --second-stage

debootstrap 的两阶段设计正是为交叉而生:第一阶段全部是"下载+解压",在什么架构的主机上都能干;第二阶段要执行 rootfs 里的 ARM 程序去配置系统——这就轮到 qemu 登场了。要用 sudo 是因为要创建设备节点、设置文件属主。

两个小提醒

目标目录必须不存在或为空——debootstrap 拒绝在非空目录里开工,重来一次之前先 sudo rm -rf rootfs 清场。另外第一阶段要下载整套基础包,镜像源选对了(例中清华 tuna)速度才有保障。

第二阶段会刷很长一串输出(以 24 核机器为参考约 20-40 分钟——qemu 逐条翻译 ARM 指令,这个耗时属于正常,不是出了问题),最后看到这行才算成功:

I: Base system installed successfully

至此 rootfs 是一个"能启动但几乎什么都没有"的 Debian——没有密码、没有 ssh、没有网络配置,接下来逐步补齐。

qemu-user-static:让 x86 主机"装作"是 ARM

qemu-arm-static 是一个静态链接的用户态模拟器:它把每一条 ARM 机器码翻译成 x86 再执行,遇到系统调用,又按 ARM 的 ABI 语义转交给本机内核。它模拟的不是整台机器,而是"一个跑 ARM Linux 程序的环境",所以叫 user-mode。

妙处在于你从头到尾不会显式调用它:安装 qemu-user-static 时,apt 会在内核的 binfmt_misc 机制里注册一条规则——此后任何进程试图执行 ARM ELF 文件,内核都自动把它路由给 qemu-arm-static。于是 chroot 里的 /debootstrap/debootstrap(ARM 程序)就"不知不觉"地跑起来了。

为什么必须先 cp 进 rootfs?chroot 的字面意思就是"换根":进去之后进程只见 rootfs 这棵树,宿主机的 /usr/bin 它看不见。代价是速度(逐条翻译),对 debootstrap 这种一次性任务完全无所谓。

第二步:配置文件——哪些从外面写,哪些必须进 chroot

接下来是一批配置。原则很简单:纯文本的,从宿主机直接写进 rootfs 最省事;要"执行程序、改变系统状态"的,必须进 chroot 让 qemu 去跑。

配置方式说明
sources.list宿主机写文件国内镜像 + trixie 全仓库,进 chroot 装包才能快
hostname宿主机写文件一行文本
fstab宿主机写文件两个分区各就各位
10-eth.network宿主机写文件网卡静态 IP(systemd-networkd)
安装软件包chroot 内执行要跑 apt/dpkg,自不必说
root 密码chroot 内执行chpasswd 要执行加密
sshd 允许 root 登录chroot 内执行改配置后顺手验证
开机自启服务chroot 内执行systemctl enable

先从宿主机把四个纯文本写掉(用编辑器或 tee 都行,例如):

cd ~/zynq-mainline
echo z7nano | sudo tee rootfs/etc/hostname
sudo mkdir -p rootfs/etc/systemd/network       # 10-eth.network 的目录默认不存在
步骤 · rootfs/ 里的文件归 root 所有

普通编辑器直接创建会遇到 Permission denied,统一用 heredoc 写入(以 sources.list 为例,其余三个同理):

sudo tee rootfs/etc/apt/sources.list <<'EOF'
deb https://mirrors.tuna.tsinghua.edu.cn/debian trixie main contrib non-free-firmware
EOF

四个文件的内容逐一给出:

# rootfs/etc/apt/sources.list —— 国内镜像,main + contrib + non-free-firmware
deb https://mirrors.tuna.tsinghua.edu.cn/debian trixie main contrib non-free-firmware

non-free-firmware 仓库放着各种固件包,留着以备某天某外设要固件;纯 main 也够本手册用。

# rootfs/etc/hostname
z7nano

# rootfs/etc/fstab —— rootfs 在 SD 第二分区,FAT 第一分区挂在 /boot
/dev/mmcblk0p2  /      ext4  errors=remount-ro  0 1
/dev/mmcblk0p1  /boot  vfat  defaults            0 2

# rootfs/etc/systemd/network/10-eth.network —— 两个名字都匹配,静态 IP
[Match]
Name=eth0
Name=end0

[Network]
DHCP=no
Address=192.168.1.10/24

networkd 配置里为什么同时写 eth0 和 end0?网口在系统里的名字有讲究,详见 4.5 节第二堂课;如果你的网络环境有 DHCP,把 DHCP=no 和 Address 行换成 DHCP=yes 即可。

第三步:进 chroot 收尾——装包、密码、服务

# 进入 chroot;从这里开始,每个程序都是 ARM 的,由 qemu 悄悄翻译执行
sudo chroot rootfs /bin/bash

# ———— 以下命令都在 chroot 内执行 ————
apt update
apt install -y openssh-server nano sudo
echo 'root:root' | chpasswd                          # root 密码 = root
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin yes/' /etc/ssh/sshd_config
systemctl enable ssh systemd-networkd                # 开机自启
exit

小提示:systemctl enable 在 chroot 里只做"创建符号链接"这件事,恰好是我们想要的;而 start 这类要和真正的 init 通信的操作在 chroot 里做不了,也不需要做——上电后 systemd 自然会把它们拉起来。

第四步:把内核模块装进 rootfs

# 4.3 节装出来的模块树,整棵拷进 rootfs(注意 lib/modules/$KVER 层级!)
# 前提:与上面导出 KVER 的步骤在同一 shell;换了终端要先重跑导出,否则 $KVER 为空
sudo mkdir -p rootfs/lib/modules
sudo cp -a $HOME/zynq-mainline/build/modules/lib/modules/$KVER rootfs/lib/modules/
# 删掉两个指向"编译机内核源码树"的软链接,板上根本不存在,留着硌脚
sudo rm -f rootfs/lib/modules/$KVER/build rootfs/lib/modules/$KVER/source
# qemu 解释器用完即弃(制卡脚本还会再删一遍,双保险)
sudo rm -f rootfs/usr/bin/qemu-arm-static

u-boot(ELF)~/zynq-mainline/build/uboot/第 6 章 JTAG 调试备用

4.5 设备树三堂课

移植过程中最容易让新手困惑的三个问题,单独开三堂课讲透——每一课背后都有一个真实踩过的坑。

第一课:这棵设备树里为什么没有 pinctrl?

习惯了 i.MX、树莓派设备的读者会发现:我们的 dts 里找不到任何引脚复用(pinctrl)节点。这是Zynq-7000 的设计:它没有 pinctrl 子系统——54 个 MIO 引脚的复用与电气配置,全部由 FSBL 执行的 ps7_init(数千条寄存器写操作)在内核启动之前完成。

这正是第 2 章"FSBL 的灵魂是 ps7_init"的另一面:设备树只描述"有哪些设备",不管"引脚怎么接";引脚归 FSBL 管,参数每块板不同,藏在 Vivado 硬件工程(厂商 hdf)里。推论:如果某个外设引脚功能不对,改设备树是没用的,得改 ps7_init 重新生成 FSBL。

第二课:网口为什么叫 end0,不叫 eth0?

新系统里 ip link show eth0 会得到 "does not exist",板上的网口叫 end0——en = ethernet,d = device-tree,0 = 设备树里的序号。这是 systemd/udev 的"可预测网络接口名":传统 eth0 按 probe 顺序编号,换内核可能变名;可预测名从设备树来,永远稳定。

dmesg 里 end0: renamed from eth0 就是改名现场,是排障时的铁证。想回退传统名字:内核命令行加 net.ifnames=0。但更稳的做法是像我们的 10-eth.network 那样,Match 里把 eth0 和 end0 都写上,两套命名通吃。

第三课:PHY 节点为什么连型号都不写?

ethernet-phy@1 里没有 compatible、没提 RTL8211F——这是内核通用 PHY 机制的本事:MDIO 总线初始化后,内核直接读 PHY 芯片自带的 ID 寄存器(厂商号+型号),自动挑对应驱动。所以型号不写也能工作,我们的 RTL8211F 就是裸着挂上去的。

同理,连 MDIO 地址都可以"不猜":reg = <0> 时 macb 驱动会扫描整条 MDIO 总线找出真实地址。我们写 1 是照厂商运行时设备树抄的,一把猜中;你移植新板没有参照时,写 0 是最稳的起步姿势。

离开本章前的自查清单
  1. strings .../build/uboot/u-boot.dtb | grep MicroPhase 能看到 Z7-Nano R20;
  2. 八项关键 CONFIG 全部 =y(4.3 节那条 grep);
  3. build/modules/lib/modules/ 下只有一个 6.18.0 目录;
  4. rootfs/etc/hostname 为 z7nano,10-eth.network 已就位;
  5. rootfs 里有 ssh,有密码,且 usr/bin/qemu-arm-static 已删。

清单全绿,就可以带着三件套进入第 5 章的制卡与首启了。

本章小结
  • 三件套全部来自主线/官方源码,apt 一条命令备齐工具链,全程零 Vivado;
  • 两棵同源设备树,真正的差异只有四处:uart0 控制台、512MB 内存、PHY@MDIO1+MIO46 复位、USB host(内核版多一个 QSPI 预留);
  • defconfig 的世界变了:U-Boot 走 xilinx_zynq_virt_defconfig + DEVICE_TREE 覆盖,内核走 multi_v7_defconfig,关键 CONFIG 用验证表自己盯;
  • debootstrap --foreign + qemu-arm-static 两阶段造 rootfs:纯文本配置从外面写,要执行的命令进 chroot,模块树按 /lib/modules/<版本>/ 层级拷入;
  • Zynq 无 pinctrl(MIO 归 FSBL 管)、网口叫 end0(net.ifnames=0 可回退)、PHY 型号可按芯片 ID 自动识别——三堂课的知识在第 5 章首启时都会现身。
